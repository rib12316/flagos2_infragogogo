## 1. dispatch 分发机制（算子路由的骨架）

- 三类实现与优先级：**FlagGems(DEFAULT)=150 > Vendor=100 > Reference(PyTorch)=50**（`vllm_fl/dispatch/types.py:38-40`）；默认选择顺序 `flagos → vendor → reference`（`policy.py:95-102`）
- 每次调用走 `OpManager._resolve_impl()`（`manager.py:317-362`）：候选过滤（vendor 白/黑名单 + `is_available()`）→ 按 policy 顺序匹配 → priority 降序取首个 → 缓存。`VLLM_FL_STRICT=0`（默认）时失败自动 fallback 下一实现并记忆失败（`manager.py:310`）
- 配置优先级：`VLLM_FL_CONFIG`（YAML 全量覆盖）> 环境变量 > 平台 yaml（按 `current_platform.vendor_name` 自动选 `dispatch/config/<platform>.yaml`，`config/utils.py:89`）> 内置默认
- 关键环境变量（`policy.py:376-393`、`vllm_fl/utils.py:192`）：
  - `VLLM_FL_PREFER` / `VLLM_FL_STRICT` / `VLLM_FL_PER_OP`（`op=a|b;op2=x`，per-op 强制顺序）
  - `VLLM_FL_FLAGOS_WHITELIST` / `VLLM_FL_FLAGOS_BLACKLIST[_APPEND]`（FlagGems 算子级开关）
  - `VLLM_FL_OP_CONFIG`（JSON per-op 覆盖，优先于 PER_OP，`utils.py:454-462`）
  - `VLLM_FL_DISPATCH_DEBUG=1` 打印实际选中的 impl（profiling 必开）
- **比赛红线对照**：「禁止删掉框架主要算子选择逻辑」保护的就是 `manager.py` 的 resolve/call + `policy.py` 选择顺序。优化必须通过「新增 impl / 改平台 yaml / env 切换」走 dispatch，不许绕过

## 2. MACA（沐曦）平台实际路由（`dispatch/config/metax.yaml` 全文已核验）

| 算子 | 路由 | 实现 |
|---|---|---|
| `attention_backend` | 仅 `vendor:metax`（metax.yaml:30-31） | `MacaBackend.attention_backend()`（`vendor/metax/metax.py:135-161`） |
| `silu_and_mul` / `rms_norm` / `rotary_embedding` / `topk_softmax` | `flagos → reference`（metax.yaml:33-44，vendor 不参与！） | FlagGems triton kernel，失败回退 PyTorch |
| FlagGems 黑名单 | `masked_fill(_)`（metax.yaml:47-49） | — |

**含义**：MiniCPM5 在 C500 上，decode 的标量算子全走 **FlagGems triton**（即 FlagGems 仓库的 kernel 表现直接吃进成绩），attention 走 **metax vendor**。vendor/metax 侧虽有 `silu_and_mul_maca / rms_norm_maca / rotary_embedding_maca` 实现（`impl/activation.py`、`impl/layernorm.py`、`impl/rotary_embedding.py`），但 **yaml 没让它们上场**——改 yaml 把 vendor 算子接进来做 A/B 是零代码改动的第一个实验点（属于 policy 配置而非删选择逻辑；是否合规建议官方群确认，稳妥路线是直接优化 FlagGems kernel）。

## 3. metax vendor 后端结构（`vendor/metax/`）

- `metax.py:32` `MacaBackend`：`vendor="metax"`，`is_available()` 查 `torch.cuda.is_available()`；注册 6 个 VENDOR 算子（`register_ops.py:27`）：`silu_and_mul / rms_norm / rotary_embedding / attention_backend / topk_softmax / invoke_fused_moe_triton_kernel`
- **attention 路径**（`metax.py:135-161`）：`use_mla` → FLASHMLA；否则 → **FLASH_ATTN**（MiniCPM5 是 GQA，走这条）
  - `impl/attention/flash_attn.py:73` `MacaFlashAttentionBackend` → `FlashAttentionImpl`：decode 用 `flash_attn_with_kvcache`，prefill 用 `flash_attn_varlen_func`（MACA 版 flash-attn，`impl/attention/utils/fa_utils.py:33` 守护）；小 prefill（query_len≤128）并入 decode 通路（`flash_attn.py:281`，`reorder_batch_threshold=128`）；split-fused 场景用 MACA 版 `merge_attn_states`（`flash_attn.py:24-26`）
  - **`ops/triton_decode_attention.py` / `triton_unified_attention.py` 已移植但未接线**（插件内无引用）——现成的优化候选/对照实现
  - `mla/flashmla.py`、`ops/merge_attn_states.py`：MLA 系与 MiniCPM5 无关，但 merge 逻辑被 GQA split 路径复用
- `patches/`：`cuda_wrapper`（cudart→maca 库替换）、`accelerator_compat`（torch2.8+metax API 补齐）、`fix_standalone_compile`（AOT cache 修复）、`chunk_delta_h`（triton num_stages 降级防 shmem 超限）、`topk_topp_sampler` 等；`patches/__init__.py` 末尾 `iu.has_triton_kernels = lambda: False`（C550 禁第三方 triton kernels——**C500 是否同样被禁需要开机确认**，影响 D2/D3 手段选择）
- 无独立量化算子（仅 fused_moe 里的 fp8/int8 分支）；MoE 系（`impl/fused_moe.py`）对 2B 稠密模型不触发

## 4. flaggems 后端（`backends/flaggems/`）

- `register_ops.py:29` 注册：`dynamic_per_token_quant_int8`（+10 优先级加成）、`silu_and_mul`、`gelu_and_mul`、`rms_norm`、`rotary_embedding`、`attention_backend`（返回 TRITON_ATTN）、`moe_align_block_size`、`moe_sum`、`topk_softmax`、`invoke_fused_moe_triton_kernel`、`grouped_topk`
- `impl/`：activation / normalization / rotary / quantization / fused_moe / attention / custom_attention / mla
- 具体kernel实现在 **FlagGems 仓库**（`FlagGems/src/flag_gems/`，triton 为主）→ 改 FlagGems 源码同样要 `pip install --no-build-isolation` 重装生效

## 5. compilation / CUDA Graph（`vllm_fl/compilation/`）

- `graph.py:43-55` `Graph` 按平台选 `CUDAGraph/MUSAGraph/...`；`GraphWrapper`（:80）平台无关 FULL 图捕获/重放（capture :184-230）
- 接入：`worker/model_runner.py:5383-5411`，`cudagraph_mode.has_full_cudagraphs()` → `GraphWrapper(FULL)`；`is_breakable_cudagraph_enabled()` → `BreakableCUDAGraphWrapper`（`break_graph.py` 是上游 `vllm.compilation.breakable_cudagraph` 的 re-export，attention/KV 边界切分捕获）
- **未发现 `FULL_DECODE_ONLY` 在本插件使用**（天数卡 serve 参数里有 `--compilation-config '{"cudagraph_mode": "FULL_DECODE_ONLY"}'`，是 vLLM 上游枚举）——沐曦侧 serve 命令**不带** compilation-config（见信息文档 §4.1），D5 方向要弄清沐曦侧默认 cudagraph_mode 是什么
- torch.compile：`model_runner.py:5365-5375`，`STOCK_TORCH_COMPILE` 模式 `fullgraph=True`

## 6. configs / 模型落点

- `vllm_fl/configs/` 仅 GLM-MoE-DSA 与一个 Qwen MoE 调优 JSON，**无 minicpm/llama 配置** → MiniCPM5 无现成调优表，GEMM/算子 tile 调优是空白点
- 插件不含 Llama 实现（`vllm_fl/models/` 仅 `qwen3_5.py`），MiniCPM5 由上游 vLLM 0.24 原生 LlamaForCausalLM 支持；`examples/minicpm/README.md` 有 serve 示例
- MiniCPM5 实际命中链路：
  ```
  PlatformFL.get_attn_backend_cls (platform.py:263)
    → call_op("attention_backend") → metax.yaml → MacaBackend.attention_backend (metax.py:135)
    → GQA 非 MLA → MacaFlashAttentionBackend (flash_attn.py:73)
  标量算子: rms_norm / silu_and_mul / rotary_embedding → FlagGems triton
  ```
- `platform.py:255-261`：关闭 cascade attention、cudnn prefill、trtllm 路径（平台强制项）

## 7. 计分脚本口径（`benchmarks/benchmark_throughput_serve.py` 精读）

- 本质是 **`vllm bench serve` 的包装器**：`--backend vllm --endpoint /v1/completions --dataset-name random --ignore-eos`（:157-177），即随机 token、忽略 EOS 强制输出到位
- **每个场景跑 4 轮、丢第 1 轮（热身）、汇总 = 后 3 轮平均**（`RUNS=4`/`SKIP_FIRST=1`，:47-50、:388-396）
- 成功判定：`successful_requests == num_prompts`，任一轮失败整个场景不进 summary（:390-394）
- 赋分指标 `Total tok/s` 从 `vllm bench` 输出正则提取「Total token throughput (tok/s)」（:188）= (输入+输出 tokens)/时长；ttft 红线 = Mean TTFT
- 输出：`./benchmark_results/raw_runs_<ts>.csv` + `summary_<ts>.csv`（**相对 CWD**，脚本要从 /workspace 跑才有官方路径 :438-441）
- 工作量估算（沐曦单轮）：4K 场景 256 prompts×5120 tok×4 轮 ≈ 524 万 token；16K 场景 128 prompts×17408 tok×4 轮 ≈ 892 万 token。加上精度评测（500 题×≤32K 输出），**一轮完整回归粗估 1.5~3 小时**，4 元/小时的券要精打细算：日常迭代用单轮快速测（绕过脚本直接 `vllm bench serve` 一次），提交级数据才跑官方 4 轮脚本
